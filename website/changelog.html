2.15
6 Sep 2026
Latest
Rigging, mocap retargeting & reply-quality fix
NewCharacter rigging goes end-to-end — all from natural language. 2.13: build a KineFX skeleton (biped, quadruped, or a simple chain — proportions fitted to your mesh), bind the skin (Joint Capture Proximity/Biharmonic → Joint Deform), and pose it (Rig Pose FK + Full Body IK, test poses without touching the viewport). 2.14: retarget mocap onto it — a Mixamo/FBX clip transfers onto your skeleton via Rig Match Pose → Map Points → Full Body IK, with automatic Mixamo joint mapping and a live skinned preview.
NewVision-assisted verification for rigs: after building a skeleton the agent looks at the viewport to confirm joints sit inside the mesh with plausible proportions; after skinning it applies a test pose and checks the deformation (candy-wrapper collapse, unbound areas); after retargeting it confirms the motion tracks the source.
FixedFixed the AI replying in raw backend jargon — internal parameter names like enablematchbounds, invented input-index shorthand like "IC16"/"IC18", JSON keys, tool names. Root cause: the system prompt was silently truncated to ~1800 of its ~26k characters (inherited from upstream), so the behavioral rules never actually reached the model. The full prompt is now sent, and explicit Artist-Friendly Language rules keep replies in artist terms — parameters are referred to by their human label + node path, never by internal names.
2.12
27 Aug 2026
Node layout protection
FixedThe AI was auto-layouting nodes without being asked — calling layout_nodes / layoutChildren() / moveToGoodPosition() as part of unrelated tasks, which is the programmatic equivalent of pressing L in the Network Editor and destroys carefully arranged node networks. Two-layer fix: the system prompt now explicitly forbids any auto-layout unless the user's message contains an explicit tidy/arrange request, and a hard guard in the tool dispatcher blocks layout_nodes entirely unless the user's message contains a keyword like "tidy", "auto-layout", or "rapiin".
2.11
17 Jul 2026
Houdini 22 vendor-path fix
FixedHoudini 22 (Python 3.13) was still loading the Python-3.11 vendor folder for MCP and the AI client, breaking import pywintypes/fastmcp even after v2.10's dual-Python packaging — four call sites each independently hardcoded a bare lib/ path instead of the version-aware picker. All vendor-path lookups now go through one shared resolver. Verified end-to-end against a real Houdini 22.0.368 + Python 3.13 session.
2.10
16 Jul 2026
Houdini 22 support
NewHoudini 22 ships Python 3.13 by default (up from 3.11 in H21 and earlier), and MorfyAI's vendored binary dependencies are ABI-locked to one Python minor version. MorfyAI now ships a second vendored dependency set built for Python 3.13 and picks whichever one matches the running interpreter automatically. Houdini 19.5–21 (Python 3.11) is unaffected.
2.9
14 Jul 2026
Critical release-build fix
Fixed.gitignore's *.py[cod] pattern was silently matching .pyd files too, so every Windows compiled binary extension under lib/ (numpy, pydantic_core, cryptography, pywin32, and 70+ others) had never been committed to git — and never shipped in any release zip. This is the real cause behind the MCP server refusing to start on release installs: fastmcp depends on pydantic_core's compiled backend, which was silently missing. All 75 previously-excluded binaries are now tracked and ship in the release package.
2.8
12 Jul 2026
MCP port leak fix
FixedThe v2.6 MCP port fix actually caused the release install's MCP to bind the wrong port — Houdini package env vars are merged into the single houdini.exe process's environment, not scoped per package, so the dev package's MORFYAI_MCP_PORT=9001 leaked into the release install too. The port is now derived from each install's own filesystem (whether its repo root ships the dev-only launcher_dev.py) instead, so it can't leak between installs.
